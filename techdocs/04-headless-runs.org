* Before you start

This document describes how to drive the digital twin of the Theory of the Relation from the command line, without a browser. It is addressed to readers who need results that can be regenerated exactly for a publication, for a replication, or for a batch of runs too large to perform by hand.

Since version 68 the simplest way is a run file: the interface and the command line compute it identically (section [[*Run files from the command line (since v68)][Run files]] below; the run file itself is described in [[file:03-usage-of-the-tr-digital-twin.org][document 3]]). The scripts further down remain for the analyses of the book (sweeps, batches, metrics) and assume familiarity with Node.js at the level of running a script from a terminal.

* What this is for

The simulation modus of =tr-twin.html= is plain, deterministic JavaScript: the browser only draws the result. So the app can also be driven *without a browser* ("headless") from the command line, in order to produce reproducible metrics and figures, for example the figures reproduced in this documentation and in the worked examples.

Same seed + same profile ⇒ bit-identical results. Every figure can therefore be traced back to: app version + profile + seed + run mode + number of steps.

* Install once

Node.js is required (tested with v22). Installation:

- *Windows*: the installer (LTS) from https://nodejs.org, or in a terminal =winget install OpenJS.NodeJS.LTS=;
- *macOS*: the installer (LTS) from https://nodejs.org, or =brew install node=;
- *Linux*: the package manager (=nodejs=, =npm=).

On pool computers the installation may need administrator rights. Then, once, in the folder of the twin (where =package.json= lies):

#+begin_src sh
npm install
#+end_src

This installs jsdom, the only dependency. (For scripts kept elsewhere, =npm install jsdom= in that folder, or =NODE_PATH= pointing to a =node_modules= folder.)

* Run files from the command line (since v68)

#+begin_src sh
node run.js runs/compare_parsons_luhmann.csv            # results in results/compare_parsons_luhmann/
node run.js runs/arbeiter_N1.csv --lang de --out mein_ordner
#+end_src

The examples in =runs/= (the contract tables of the book serve only as examples of how the data mode works):

| run file | what it computes |
|---+---|
| =compare_parsons_luhmann.csv= | Parsons and Luhmann next to the TR, 1819 steps, seeds 1–8 |
| =vergleich_theorien.csv= | several theory profiles next to the TR (German keys) |
| =vergleich_kuehl_meyer_rowan.csv= | the profiles of Kühl and Meyer/Rowan (coded by a student) next to the TR without mechanisms (=profil_TR_ohne_Mechanismen.csv=) and the TR with them |
| =reiz_kuehl_meyer_rowan.csv= | the same with a stimulus (economy weakened after 1819 steps) and the control runs; about 2 minutes |
| =reiz_politik.csv= | a stimulus on politics, with the control run |
| =arbeiter_N1.csv= | data mode: a contract table of the book (chapter 11), as an example of the data mode |
| =ouvriers_N1_instances.csv= | data mode with instances (French keys) |
| =kapitel12_variante_a.csv= | data mode, a contract table of the book with empty years carried forward: an example whose outcome depends on the seed |
| =prism_probes.csv=, =worked_example.csv= | prism probes; the worked example of document 3 |

=run.js= loads =tr-twin.html= with jsdom and calls the same functions as the interface: reading the run file, the runs (TR and theories × seeds, or the cohort × seeds), the tables and the figures. It writes =report.html=, =tables.csv=, one CSV per table in =tables/=, =series.csv= and the figures in =figures/=. =--lang= sets the language of the tables and figures (=en=, =de=, =fr=). Paths in the run file are relative to the run file.

The simulation runs of a run file are the runs of the pipeline (=__setze= and N steps), the year runs those of =run.js= below (=runSeries=), the data runs those of the cohort import of the interface; with the same settings their results are bit-identical (=tests/test_v67_equal.js=). The interface and the command line give the same tables and series for the same run file (=tests/test_gui_cli.py=).

Concretely:

#+begin_src sh
node simulation-mode/scripts/runs/run_steps.js  ./tr-twin.html  ./simulation-mode/profiles/profil_Parsons.csv  1819  ./out/parsons.json

The cursors are set to the profile's last-year values and held constant; this is the mode behind the trajectory figures ("neutral scenario, seed 1, 1819 steps").

* How it works (three lines)

1. *Load*: =jsdom= parses =tr-twin.html= and executes its script, which initialises everything (=reset()=, neutral reference state, cursors, timeline).
2. *Stub*: =canvas.getContext= and =requestAnimationFrame= are replaced by dummies — nothing is drawn and the animation loop never starts, so the simulation stands still until we drive it.
3. *Drive*: the app's own functions are called inside the page: =parseCursorCSV(profile)= for the cursor curves, then either =runSeries()= (year mode) or =reset()= + =step(dt)= in a loop (step mode), with =dt = 1/60*0.68=.

* Three things a profile does NOT fix

** 1. The run horizon: 1819 steps is not convergence

The twin is a dynamic model and needs time to settle. 1819 steps is the horizon of the *trajectory* figures — it is a snapshot on the way, not an end state. The end state is reached around 5000 steps, and this is the same for the sweep. Here an example with three profiles from the book:

| profile | 1819 steps | 5000 steps (settled) |
|---------+---------------------------------+----------------------------------|
| TR      | 25/25/25/25 · GINI 0.002        | 25/25/25/25 · GINI 0.001         |
| White   | 14/58/14/14 · GINI 0.329        | 13/62/13/13 · GINI 0.372         |
| Tilly   | 24/23/26/26 · GINI 0.028        | 15/16/49/19 · GINI 0.264         |

** 2. The seed: some configurations are bistable

Where a configuration is bistable there are always exactly two attractors and the seed only picks the basin. Run every apex claim over eight seeds and report in how many it holds. See =keim_audit.md= and the seed-audit section below reporting for the book.

* Producing the figures

The figures of the book are produced in two steps: *(1)* a headless run writes the numbers to JSON, *(2)* a small Python renderer draws the SVG in the report style. Nothing is drawn by the browser, and every figure can be regenerated from the app + a profile.

** The metrics written to JSON

=S= (sizes of the four structures), =gini= (transversal inequality), =recip= (reciprocity), =sat= (satellisation), =ruler=, =resid= (overload), =structRecip=, =structGini=, =vertGini= (vertical inequality per structure) — and =crossOff=.

*** crossOff — the volume of inter-structural circulation

=crossOff= is not a function of the app; it is derived from the app's =crossViz= matrix, which smooths the cross-structural actor flows computed in =migrate()= (=crossViz[x][y] += 0.12*((cf[x][y]/dt) - crossViz[x][y])=, where =cf= are exactly the flows that leave a structure). The figure metric is the sum of the off-diagonal entries:

#+begin_src js
let crossOff = 0;
for (let x=0;x<4;x++) for (let y=0;y<4;y++) if (x!==y) crossOff += crossViz[x][y];
#+end_src

crossOff is strongly mig-dependent and must always be quoted with both the horizon and the migration. At mig 1.4 the same three profiles read TR 0.578 · White 0.581 · Tilly 0.417 — White returns to the TR level while Tilly stays blocked, which is the comparison chapter 6 makes in the book. Quoting a crossOff without stating mig and the step count is meaningless: for Tilly the value runs from 0.260 (1819 steps) through 0.126 (settled, mig 0.7) to 0.417 (settled, mig 1.4).

** Rewiring the network: the hub profiles

Chapter 6 (White) asks whether the apex simply follows the network position, as pure structural equivalence would require. The test rewires the network four times, each time making one position the /hub/:

- every non-hub structure gets a chain whose *first* entry is the hub, so its circulation is directed at the hub;
- the hub's own chain runs through the remaining structures in unchanged (index) order;
- everything else — including White's cursors (rate 1.8, alpha 1.6) — stays identical.

The four files are =profil_White_hub_A.csv= … =profil_White_hub_D.csv= (A culture, B politics, C economy, D media). Run them like any other profile:

#+begin_src sh
node simulation-mode/scripts/runs/metrics.js ./tr-twin.html ./spec_white_hub.json ./out/white.json
#+end_src

with a spec listing the four profiles at 5000 steps (the apex is not settled at 1819). Result (seed 1):

| hub          | K    | P    | W    | M    | GINI  | apex          |
|--------------+------+------+------+------+-------+---------------|
| A culture    | 27.0 | 24.5 | 22.9 | 25.6 | 0.033 | none (< 0.05) |
| B politics   | 12.5 | 60.2 | 13.1 | 14.3 | 0.361 | B 60 %        |
| C economy    | 15.2 | 16.4 | 49.6 | 18.8 | 0.263 | C 50 %        |
| D media      | 15.3 | 15.9 | 53.7 | 15.0 | 0.291 | *C* 54 %        |

The apex therefore follows the hub neither reliably nor with equal strength — the residual gradient favours the economy. Over eight seeds (=keim_audit.md=) three of the four are bistable; only hub=B holds in 8/8.

Note on chain semantics: =setChain(x, o)= gives =WT[x][o[0]] = 3/6=, =WT[x][o[1]] = 2/6=, =WT[x][o[2]] = 1/6=. The first entry of a chain is the structure that *gains*: pointing all chains at one structure makes that structure grow. Chains also silence the =plast= cursor for every structure they fix (see the pitfalls above).

* Two fixes applied to the app

The audit produced two changes to =tr-twin.html= itself.

** 1. =reset()= now clears the satellisation

: function reset(){reseed();rulerHold=[0,0,0,0];satS=[0,0,0,0];S=[0.25,0.25,0.25,0.25]; ...

=satS= and =rulerHold= survived =reset()=, so consecutive runs in one page inherited the previous run's satellisation — including the app's own =runSeries()=. All ten callers of =reset()= were checked; only the series function at the end of the file relies on the old behaviour, and it restores =satS= *after* calling =reset()=, so the order still holds. =playScnFrom()= already zeroed both explicitly and is now simply redundant.

The headless scripts kept their own =satS=[0,0,0,0]; rulerHold=[0,0,0,0];= line: it is harmless with the fixed app and keeps the scripts working against older copies.

** 2. The =plast= cursor now shows when it has no effect

Chains fixed by a profile silence the plasticity for those structures.  The cursor stayed fully operable and silently did nothing. A new =syncPlastState()= greys the slider out when a profile fixes all four chains, adds a tooltip, and writes a short red note next to the label. It is called once at start-up and after every profile import.

** What was deliberately not "fixed"

The bistability (see below) is not a defect but a property of the model, and the sensitivity at the bifurcation point is the phenomenon itself. Neither was touched.

* Seed audit: which findings are seed-stable?

=metrics.js= accepts a =seed= per entry in the spec:

#+begin_src js
[{"label":"Tilly K1", "profile":"./simulation-mode/profiles/profil_Tilly.csv", "steps":5000, "seed":1}]
#+end_src

Running every apex configuration of the book over eight seeds (120 runs) gives: ten findings are seed-stable, five are not. Where a configuration is bistable there are always *exactly two attractors* and the seed only picks the basin; the politics attractor is the stronger one and wins even when every chain points at another structure. Bistability appears only at high concentration (alpha 1.6); at alpha 1.4 the same construction is stable. Criterion: GINI ≤ 0.05 means "no domination" — in a symmetric field the argmax is meaningless. Full table: =keim_audit.md=.

* Stimulus protocol and stimulus threshold (v65, v66)

Since v65 the twin computes a stimulus itself. A stimulus is a deliberate change of /one/ relational
structure at its core sequence, for a set time. It is not a way of showing which structure rules, but a test of
whether the targeted change prevents the return to the state the run would reach without it.

| Call | What it does |
|------+--------------|
| =reizSetzen(x, dir, dauer, k)= | starts a stimulus on structure =x= (0–3) now: =dir= +1 strengthen, −1 weaken; =dauer= in steps of 1/60·0.68; strength =k= (default 2.6) |
| =reizStop()= | ends it |
| =setMech({M1, …, M6})= | switches the satellisation mechanisms on or off; =SATDAUER= sets the saturation time of M5 (default 40). Since v67 =applyDefaults()= switches all six on (the TR), and =profilMech(parseCursorCSV(csv))= sets those a profile declares (row =mechanismen,…=; none declared = none) |
| =reizLauf(o)= | from =reset()=: =o.beginn= steps (1819), stimulus for =o.dauer= steps (300), =o.nachlauf= free steps (6000); =o.ohne= = the same length without stimulus |
| =reizProbe(o)= | stimulus run and control run; =urteil= "zurueck", "fest" or "bewegung" |
| =reizSchwelle(o, dauern)= | the shortest duration in =dauern= with the verdict "fest", and the whole series |

- /Strengthen/ adds =k·dt= to the core sequence =g[x][x]= (the operation of holding a circle pressed).
- /Weaken/ (v66) moves =k·dt= of the leading sequence =R = ruler[x]= to the next sequence along the butterfly path of
  the leading structure (largest size + 2 × smoothed growth, other than x), skipping the structure's own sequence;
  once =R= is the leader's core, it takes from the own core instead. Without a clear leader: the order A→B→C→D→A
  (=REIZ_FOLGE=), skipping the own sequence. The weakening never brings a structure back to its own core.
- /M1/ chain alignment: the chain of a satellised structure is pulled toward the order of the satelliser's path
  (rate =KCHAIN·satS=); its own plasticity is scaled by =1 − satS=. Chains fixed by a profile stay fixed.
- /M2/ regime takeover: satellised above 0.5 for 2.0 time units, the structure runs under the satelliser's
  sequence (=ruler = satelliser=); released below 0.2.
- /M3/ mediate strengthening: the satelliser's instance types (relation, sequence, sub-sequence, control),
  weighted by the square of their strength relative to its strongest one, strengthen the same types in each
  satellite at the rate =KM3·satS=.
- /M4/ control of the satellite (=ctrlSat=: alienated share of control, at most 0.8); /M5/ saturation of domination
  (=Zsat=), erosion until another structure is stronger by 0.03; /M6/ force of control (=Phi=: diversification and
  networking of the instances). =reizLauf= returns these with each moment and the changes of domination of the free
  run in =verlauf=.
- Verdicts: /zurueck/ — no size deviates by 0.03 or more from the control run at the end; /fest/ — one does, and
  the run is at rest; /bewegung/ — a size still changes by 0.005 or more over the last 1000 steps. With 1500 free
  steps a slow transient can look "set"; the default of 6000 avoids that.

#+begin_src js :eval no
setMech({M1:true, M2:true, M3:true});
const p = reizProbe({x: 2, dir: -1, beginn: 1819, dauer: 800, nachlauf: 6000});
p.urteil, p.abw, p.mit.ende.S, p.mit.ende.ruler, p.mit.ende.ketten
#+end_src
